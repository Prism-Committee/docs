# 运维与故障处理

这一页集中处理 WebShopX 上线后的高频运维问题：交付失败、退款、库存异常、备份、升级和日志排查。

## 1. 先建立日常运维基线

上线后至少持续关注：

- 登录与会话是否正常；
- 订单是否能从创建推进到交付；
- `WAIT_CLAIM` 是否持续堆积；
- 信箱待领取数量是否异常增长；
- 退款量和退款失败原因；
- 市场成交、下架和补货异常；
- 业务日志与审计日志是否有重复操作或权限异常。

## 2. 发货、领取与信箱

常见订单状态：

| 状态 | 含义 |
| --- | --- |
| `PENDING` | 待处理 |
| `WAIT_CLAIM` | 需要玩家手动领取 |
| `DELIVERED` | 已交付 |
| `REFUNDED` | 已退款 |
| `CANCELLED` | 因退款或业务取消而终止 |

自动交付失败后，系统可能回退到 `WAIT_CLAIM`。玩家可使用：

```text
/ws claim [all|ODR-|MKT-|CLM-|MCL-]
/ws mailbox
/ws mailbox collect
```

如果背包无法接收物品，交付内容可能进入信箱。

### 排障顺序

1. 检查订单/交易当前状态；
2. 检查玩家是否在线以及背包空间；
3. 检查是否已经生成领取 token；
4. 查看信箱是否存在待领取物品；
5. 再根据业务日志判断是否需要补偿，而不是直接手工补发。

## 3. 退款

退款能力受当前版本和后台策略共同控制。处理退款问题时至少确认：

- 订单是否已经成功交付；
- 当前订单是否还在允许退款的时间窗口；
- 是否已经退款；
- 团购券或其他特殊商品是否已消费；
- 市场订单是否涉及卖家结算或冻结资金。

不要只根据玩家截图判断退款状态，应以后台订单记录、业务账本和审计日志为准。

## 4. 网页背包与离线库存

在线库存以服务器运行时中的真实玩家库存为准。离线查看或离线写入属于不同能力：

- **离线只读**：用于展示历史/最近可用库存，不应作为权威库存做人工补发依据；
- **离线即时写入**：属于实验性高风险能力，只应在明确支持的版本和后台开关下使用。

:::danger[离线写入]
不要根据旧文档手工添加未出现在当前 `config.yml` 的 YAML 字段来开启离线库存写入。是否支持、如何启用，应以当前版本后台设置和实际实现为准。
:::

启用实验性离线库存能力前，至少满足：

1. 单实例部署；
2. 已完整备份世界和玩家数据；
3. 没有其他插件或跨服系统同时直接写 playerdata；
4. 已在相同服务端版本的测试环境验证；
5. 出现复制、丢失或损坏迹象时立即关闭相关能力并保留日志。

## 5. 备份与升级

升级前建议：

1. 停服或进入维护窗口；
2. 备份数据库；
3. 备份 `plugins/WebShopX/` 数据目录；
4. 如启用了实验性离线库存能力，同时备份玩家数据；
5. 替换 JAR 后启动并验证登录、下单、市场、领取、退款和后台权限。

生产环境不要把“能启动”当成升级成功。关键业务流程至少完整跑一轮。

## 6. 集群与 Relay 故障

多节点环境还需要检查：

- 各节点版本一致；
- `server-id` 唯一；
- Redis 可连接且频道配置一致；
- runtime 配置更新能在节点间同步；
- Relay 模式下实例绑定、访问密钥和连接状态正常。

部署相关配置见 [安装与部署](./install-deploy)。

## 7. 权限、审计与安全

- 管理员操作应通过后台角色和权限体系控制；
- 高风险操作尽量让 `USER_SUPPORT`、`ECONOMY_MANAGE`、`MARKET_MANAGE` 分离；
- 修改余额、强制下架、退款和管理员变更后应检查审计记录；
- 数据库密码、Relay access key、支付密钥不要出现在公开 Issue 或截图里。

## 8. 仍无法定位问题时

记录以下信息再提交 Issue：

- WebShopX 版本；
- Minecraft / Paper / Purpur / Spigot / Folia 版本；
- Java 版本；
- 单服还是集群；
- 数据库类型；
- 可复现步骤；
- 相关错误码和日志片段；
- 是否安装 Vault、WebShopX-Payments 或其他库存/经济插件。

问题反馈仓库：<https://github.com/Prism-Committee/WebShopX-Issues>
